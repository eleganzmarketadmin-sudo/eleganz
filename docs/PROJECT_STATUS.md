- **(12 oct.) Nouveau module : Espace Livreur** (troisième grand espace de la plateforme, après Gestion et Marketplace — prompt §10). Le backend des missions existait déjà partiellement (affectation, confirmation d'enlèvement/livraison), mais aucun livreur ne pouvait ni s'inscrire ni se connecter : c'est maintenant complet.
  - **Inscription et connexion** (`/livreur/inscription`, `/livreur/connexion`) : un livreur crée un compte (rôle `DRIVER`) puis son profil (zone/commune), toujours créé **non vérifié** — aucune mission réelle n'est affectable à un livreur non vérifié (`assignDriver` le bloque déjà côté serveur).

  - **Non couvert dans cette première passe, à prévoir plus tard** : rémunération/règlement des livreurs (aucun tarif n'existe encore, le prompt §56 interdit de graver un tarif commercial dans le code — à concevoir avec le propriétaire du projet) ; signalement d'incident de livraison distinct du litige acheteur (actuellement, seul le passage en litige par la boutique existe) ; offres professionnelles multi-livreurs pour une entreprise logistique (prompt §28).

## Ce qui bloque sur une décision ou une ressource externe (pas du code)

- **Paiements réels (Moneroo, Orange/Airtel/Vodacom)** : aucune intégration de paiement n'est branchée. Il faut un compte marchand Moneroo (et, plus tard, les contrats opérateurs) avec de vraies clés API avant de pouvoir coder l'appel réel — je ne peux pas créer ce compte ni obtenir ces clés moi-même.
- **Planificateur de tâches** (expiration d'essai, suspensions, relances) : fonctionne aujourd'hui par déclenchement manuel admin. Passer à un vrai cron nécessite de décider où le processus tournera (même serveur que l'API, ou un worker séparé) — lié au choix d'hébergement, pas encore fait.
- **Services IA** (recherche par photo, studio publicitaire, assistant marketing) : nécessitent de choisir et de payer un fournisseur (OpenAI, Google Vision, Replicate, etc.) — aucun n'est engagé.
- **Hébergement/déploiement** : aucun compte VPS, domaine ou stockage objet n'a été créé.

## Limite connue de cet environnement (pas un défaut du code)

`pnpm db:generate` (génération du client Prisma) échoue dans ce bac à sable car `binaries.prisma.sh` n'est pas sur la liste des domaines autorisés en sortie. Fonctionnera normalement sur un poste de dev ou un CI avec accès réseau complet — détails dans `MAINTENANCE.md`. Tant que ce n'est pas généré ici, `apps/api` ne peut pas être compilé/testé dans cette session (il dépend des types générés par Prisma).

- **Mode hors-ligne de la caisse — phase 1 implémentée** (`docs/ARCHITECTURE_HORS_LIGNE.md`, décision #8) : le propriétaire a validé la politique de stock négatif en synchronisation différée (accepter la vente, stock négatif, écart signalé — jamais de rejet après coup d'une vente déjà réellement encaissée). Côté API : `clientOperationId` idempotent sur `PosSale`, `PosSaleLine.stockDiscrepancy`, `POST /shops/:shopId/pos/sales/sync`, `GET /shops/:shopId/pos/stock-discrepancies`. Côté écran : file IndexedDB (`offline-queue.ts`), synchronisation automatique au retour réseau et par intervalle (`offline-sync.tsx`), bascule automatique de la caisse vers la file hors-ligne quand le serveur est inatteignable, indicateur « ventes en attente » dans l'en-tête Gestion, liste des écarts de stock dans le tableau de bord.

- **Images produits par URL** (`PATCH /shops/:shopId/products/:productId`, écran catalogue) : une boutique peut maintenant attacher des photos hébergées ailleurs à un article — pas d'upload (aucun compte de stockage objet encore), mais la vitrine et la fiche produit Marketplace affichent déjà la vraie photo quand elle existe.
- **Mode hors-ligne — phase 2 implémentée (app shell installable)** : manifest (`public/manifest.json`, nom/icônes/couleurs ELEGANZ, `start_url: /caisse`, `display: standalone`), icônes réelles (192/512, générées en Python puisque la conversion SVG→PNG par ImageMagick n'était pas disponible), service worker (`public/sw.js`) qui met en cache les pages déjà visitées et les fichiers statiques *à l'usage* (pas de préchargement au build — `next build` ne peut pas tourner dans ce bac à sable, voir `MAINTENANCE.md`), page de secours hors-ligne (`public/hors-ligne.html`, HTML statique indépendant du rendu Next.js), enregistrement du service worker (`components/ServiceWorkerRegistration.tsx`) et lien du manifest + couleur de thème dans `app/layout.tsx`. Le service worker ne touche jamais aux appels vers l'API — la file hors-ligne de la caisse (phase 1) s'en occupe déjà. `tsc --noEmit` validé après ces changements.

- **Rendu PDF des commandes Marketplace** (`POST /shops/:shopId/documents/shop-order/:shopOrderId`, bouton « Imprimer le bon de livraison » dans `/commandes`) : le rendu PDF couvre maintenant aussi les sous-commandes Marketplace (`shopOrderId`), pas seulement les ventes de caisse. Comme aucun paiement en ligne n'est encore branché (décision #2), le document affiche une note « paiement à la livraison » plutôt que d'inventer un paiement confirmé. Au passage, l'écran `/commandes` affiche maintenant le vrai nom de l'article (et taille/couleur) au lieu d'un simple « Article ».

- **Upload réel d'images produits** (Cloudflare R2, décision du 11 octobre 2026) : remplace le collage d'URL manuel. `StorageService` génère une URL R2 signée à durée limitée, le navigateur de la boutique y envoie directement le fichier (jamais via notre serveur), seule l'URL publique finale est enregistrée sur l'article.
